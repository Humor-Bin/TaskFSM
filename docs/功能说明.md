# TaskFSM 功能说明

## 1. 产品定位
TaskFSM 是一个 **Agent 任务监测、可视化与可选调度平台**。

系统支持两种对等模式：

- **Observe Mode**：任务与执行来自 Agent 内部，TaskFSM 只读取外部可观察事实并投影成统一 Task/Run，不拥有调度权。
- **Managed Mode**：任务由 TaskFSM 管理，TaskFSM 负责 Claim、Lease、Run、FSM Guard、Artifact、Review，并可启动 Agent 执行。

因此 TaskFSM 同时支持：

```text
Agent -> TaskFSM   （观察）
TaskFSM -> Agent   （调度）
```

初期具体 Agent 只支持 Codex CLI。

## 2. Codex Observe Mode
TaskFSM 默认扫描 `CODEX_HOME/sessions/YYYY/MM/DD/rollout-*.jsonl`。

Observe Mode 不再把“Session ID”直接当作人类任务名，而是建立一层 **Semantic Projection（语义投影）**：

```text
Codex rollout
  -> Session identity
  -> 用户任务意图
  -> 当前可见活动
  -> Agent Plan
  -> Workspace / Git branch
  -> Runtime status
  -> 人类可读 Task Projection
```

可识别并投影：

- Codex Session ID
- Workspace 完整路径与工作区名称
- Git Branch（工作区为 Git 仓库时）
- 第一条用户消息形成的“任务意图”
- 人类可读任务标题
- Agent 当前可见活动
- 原生 Plan 快照
- 等待用户输入状态
- Session 最近活动时间
- 活跃 / 等待输入 / 已结束 / 异常运行态

例如 Codex 原始事件：

```text
item_started / command_execution / pytest tests/test_importer.py -q
```

TaskFSM 展示为：

```text
正在执行命令：pytest tests/test_importer.py -q
```

而不是直接展示内部事件类型 `AgentMessage`、`command_execution` 等协议字段。

Observed Task 使用：

- `source = codex`
- `control_mode = observed`
- `external_id = Codex Session ID`

Observed Task 是外部状态的投影，因此：

- 不进入 Agent 可领取任务列表
- 不创建 TaskFSM Lease
- TaskFSM 不能人工把它标记完成
- UI 只展示其任务意图、当前活动、Plan、Session、Workspace 和事件

### 活跃状态判断

仅仅存在 rollout 文件不代表 Session 正在执行。TaskFSM 使用最近文件活动时间作为保守运行态信号：

```text
TASKFSM_CODEX_ACTIVE_WINDOW=300
```

默认 300 秒内仍有 rollout 活动的 Session 可视为活跃；超过窗口且没有明确等待状态的历史 Session 会进入 `ended` 投影，不再全部堆到“进行中”。

该状态表示“最近是否仍有可见 Codex 活动”，不是对操作系统进程存活的绝对保证。后续可进一步叠加 PID/tmux/hook 信号提高准确度。

默认自动同步可通过：

```text
TASKFSM_CODEX_AUTO_SYNC=1
TASKFSM_CODEX_SYNC_INTERVAL=5
```

控制。Web 仍提供“同步 Codex”按钮用于手动强制刷新。

## 3. Codex Managed Mode
Managed Mode 默认关闭，因为它允许服务端启动本机进程：

```text
TASKFSM_CODEX_MANAGED=1
```

启动流程：

```text
Task Ready
  -> TaskFSM Claim
  -> Run + Lease
  -> CodexRuntimeManager
  -> codex exec --json
  -> Codex CLI
```

Runner 会注入 Task / Run / Agent / Lease 环境变量，并读取 CLI JSONL 作为运行遥测。

重要边界：**Codex CLI 输出不是业务状态命令。** 即使 Codex 输出“任务完成”，TaskFSM 也不会直接把 Task 标记为 Done。

## 4. Codex Plugin / Skill / MCP
TaskFSM 提供 Codex Plugin：

```text
integrations/codex-plugin/
  .codex-plugin/plugin.json
  .mcp.json
  skills/taskfsm-worker/SKILL.md
```

MCP Server 位于：

```text
packages/taskfsm-mcp/
```

Managed Codex 可调用：

- `get_current_task`
- `heartbeat`
- `report_progress`
- `submit_artifact`
- `request_review`

Skill 负责规定操作顺序，MCP 负责真实业务动作，Runner 负责进程控制与遥测，TaskFSM Server 仍是唯一 FSM 裁决者。

Codex 内部 todo / plan 只作为 Run 的执行细节展示，不自动转换为 TaskFSM 子任务，也不直接计算业务状态。

## 5. 前端运行控制台
运行视图明确拆成两套状态体系，避免“94 个历史 Session = 94 个进行中任务”的误导。

### Agent Runtime
仅用于 Observed Session：

- 活跃 Session
- 等待输入
- 历史 Session
- 异常

### Managed FSM
仅统计由 TaskFSM 拥有生命周期的任务：

- 任务池
- 待办
- 就绪
- 进行中
- 待审查
- 阻塞
- 完成

### 任务详情的阅读优先级

详情页首先回答人类最关心的四个问题：

1. **当前任务是什么？** —— 展示用户任务意图，而不是 Session ID。
2. **现在在做什么？** —— 展示人类化后的当前活动。
3. **在哪里执行？** —— Workspace、完整路径、Git Branch、Session、Run。
4. **做到哪一步？** —— 展示 Agent 原生 Plan；没有 Plan 时明确说明，不伪造。

历史 Session 默认不会占满中央运行关系图；运行区优先展示活跃、等待输入、异常 Session 和 Managed 活跃任务。

## 6. Managed Task 状态机
Managed Task 服务端维护唯一可信业务状态。Agent 只能调用动作接口，不能直接 PATCH 状态。

关键规则：

- `ready -> in_progress`：能力匹配、依赖完成并 Claim
- `in_progress -> review`：有效 Lease + 依赖完成 + 至少一个 Artifact
- `review -> done`：存在 approved Review + 依赖完成
- `in_progress -> done`：禁止
- Lease 过期：Managed Task 可回收到 ready

Observed Task 不使用上述调度状态机作为权威来源。

## 7. Task / Run / Session 的关系
- **Task**：统一的人类可理解任务投影
- **Run**：一次具体执行
- **External Session**：Codex 自己的原生会话 ID
- **Lease**：仅 Managed Run 使用的 TaskFSM 临时执行所有权

Observed：

```text
Codex Session -> Semantic Projection -> Task + Observed Run
```

Managed：

```text
TaskFSM Task -> Managed Run -> Lease -> Codex Session
```

## 8. Artifact / Review
Artifact 是一等对象，支持 file、url、git_commit、pull_request、report、json 等类型。

Managed Agent 提交 Artifact 后才能请求 Review。Review approved 后，人类才能完成任务。

Observed Session 当前只做只读投影，不强制要求外部 Agent 使用 TaskFSM Artifact/Review 协议。

## 9. Event 与实时同步
业务动作和 Codex Runtime 都会写 Event，但两类事件含义不同：

- Domain Event：Task Claim、Lease、Artifact、Review、FSM Transition
- Runtime Event：Codex Session、CLI JSONL、当前活动、进程退出

Runtime Event 只能影响运行视图；只有 Domain Action 可以改变 Managed Task 业务状态。

前端通过 `/api/events/stream` SSE 感知变化，通过 `/api/dashboard` 获取最新投影。

## 10. Agent SDK
通用 Python Agent SDK 仍保留，用于后续接入非 Codex Agent。

当前初期产品不会优先扩展多 Agent 调度，而是先确保：

1. Codex 原生 Session 能无感被观察；
2. 人类能直接看懂任务、当前活动、工作区和执行计划；
3. 单个 Codex Managed Run 能被可靠启动和监督；
4. 两种模式在统一 UI 与 Event 模型中共存。

## 11. 安全边界
当前版本适合本地或受控网络：

- Agent Bearer Token 已实现
- Managed Codex 默认关闭
- Browser 不持有 Agent Token
- MCP Token 通过 Managed Runner 环境变量注入
- 人类 OIDC / Session / RBAC 尚未实现
- CORS 当前仍为开发态宽松配置
- 本地 Runner 启动的是服务器所在主机上的 Codex CLI

因此在补齐人类身份认证、Workspace 白名单和进程隔离前，不应把 Managed Run API 直接暴露到公网。

## 12. 后续演进
优先顺序：

1. Codex Session 增量读取 / 文件监听，减少全量扫描成本
2. 使用 Hook / PID / tmux 等信号提高 Session 活跃状态准确率
3. Managed Workspace 白名单与 Git Worktree Manager
4. 人类 OIDC / RBAC
5. Alembic 数据库迁移
6. Redis Pub/Sub 或 NATS 多实例事件总线
7. Codex Resume / Stop / Prompt Queue
8. 第二种 Agent Adapter
9. 多 Agent 调度与协同

TaskFSM 不以“尽快支持最多 Agent”为当前目标，而以“先把单 Codex 的观察、可读语义投影与受管执行链路做稳定”为目标。
